# Support Ticketing System

A full-stack MVP for a support ticketing service: create tickets, browse thousands of
them efficiently, and let agents **claim** tickets with a race-safe guarantee that only
the first agent wins.

## Tech stack

| Layer    | Tech |
|----------|------|
| Backend  | Python 3.14, FastAPI, SQLAlchemy 2.0, Alembic, Pydantic v2, uv |
| Database | PostgreSQL 16 |
| Frontend | React + TypeScript, Vite, Mantine, TanStack Query, React Router |
| Tooling  | Docker Compose, pytest, Ruff, GitHub Actions |

## Quick start (Docker, recommended)

```bash
docker compose up --build
```

| Service   | URL |
|-----------|-----|
| Frontend  | http://localhost:8080 |
| API docs  | http://localhost:8000/docs |

The database is initialised automatically: a one-off `migrate` service runs
`alembic upgrade head` before the backend starts.

Optional: load 5,000 fake tickets:

```bash
docker compose exec backend python -m scripts.seed --count 5000
```

Reset everything (including data): `docker compose down -v`

## Local development (without Docker for the app)

**1. Database**

```bash
docker compose up -d db
```

**2. Backend** (in `backend/`)

```bash
cp .env.example .env
uv sync
uv run alembic upgrade head          # initialise / migrate the database
uv run uvicorn app.main:app --reload # http://localhost:8000
```

**3. Frontend** (in `frontend/`)

```bash
npm install
npm run dev                          # http://localhost:5173
```

> On Windows with Smart App Control, use `uv run python -m alembic ...` /
> `uv run python -m uvicorn ...` if the `.exe` launchers are blocked.

## Tests

```bash
cd backend
uv run pytest
```

Tests run against a separate `ticketing_test` database (created automatically), apply the
real Alembic migrations, and include a **concurrency test** that fires 20 simultaneous
claims at one ticket and asserts that exactly one succeeds.

An end-to-end race check against the running API is also available:

```bash
uv run python -m scripts.race_test --agents 20
```

## API

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/v1/tickets` | Create a ticket |
| `GET`  | `/api/v1/tickets?limit=&cursor=&priority=&assigned=&tag=` | List tickets (cursor-paginated, newest first) |
| `GET`  | `/api/v1/tickets/{id}` | Get one ticket |
| `POST` | `/api/v1/tickets/{id}/assign` | Claim a ticket → `200`, `404`, or `409 Conflict` if already assigned |
| `GET`  | `/health` | Health check (includes DB connectivity) |

## Key design decisions

### 1. Race-safe assignment ("only the first agent wins")
The ownership check and the write are a **single atomic statement**:

```sql
UPDATE tickets SET assigned_to = :email, assigned_at = now()
WHERE id = :id AND assigned_to IS NULL
RETURNING *;
```

PostgreSQL's row lock serialises concurrent claims. The first transaction updates the row;
the others re-evaluate the `WHERE` clause, match 0 rows, and receive `409 Conflict`.
This avoids the classic *check-then-act* race of "SELECT, then UPDATE", and it works across
multiple API workers/servers because the guarantee lives in the database, not in app memory.

### 2. Cursor (keyset) pagination for large datasets
`OFFSET` gets slower the deeper you page and can skip/duplicate rows while new tickets
arrive. Instead the API returns an opaque `next_cursor` encoding `(created_at, id)`, and the
next page is fetched with `WHERE (created_at, id) < (:c, :i)`, backed by a composite index.
Every page is equally fast, and `id` breaks ties for a stable order.

### 3. Data model
- `priority`: PostgreSQL `ENUM` (`low`, `medium`, `high`, `critical`) → invalid values are impossible.
- `tags`: `TEXT[]` with a GIN index → simple, fast tag filtering without a join table.
- `assigned_to` / `assigned_at`: nullable, with a `CHECK` constraint that both are set together.
- All timestamps are timezone-aware and generated by the database.

### 4. Structure
`api/routes` (HTTP) → `services` (business logic) → `models` (ORM), with Pydantic
`schemas` as the API contract. Configuration comes from environment variables and fails
fast if `DATABASE_URL` is missing.

## Trade-offs & future improvements
- **Authentication** is out of scope; the agent identifies themselves by email (remembered in the browser).
- **Tag model**: an array is ideal for this MVP; a separate `tags` table would suit tag renaming/analytics.
- **Real-time updates** (SSE/WebSockets) so other agents see claims instantly.
- **Observability**: structured logging, OpenTelemetry tracing, and metrics.
- **Ticket lifecycle**: status (open/in progress/resolved), unassign/reassign with audit history.
- **Rate limiting** on the claim endpoint.

## Project structure

```
backend/
  app/
    api/routes/   # FastAPI routers
    core/         # settings, pagination helpers
    db/           # engine, session, declarative base
    models/       # SQLAlchemy models
    schemas/      # Pydantic request/response models
    services/     # business logic (race-safe assignment lives here)
  migrations/     # Alembic migrations
  scripts/        # seed data, race test
  tests/          # pytest suite
frontend/
  src/
    api/          # typed API client
    components/
    pages/        # list + detail views
docker-compose.yml
```
